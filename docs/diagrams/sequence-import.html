Runtime behavior · async import lifecycle

Import Request — Sequence

One single-store customer import, end to end. The defining move: the run row is written to Postgres before the bulk mutation is ever submitted, so a crash can only ever leave a recoverable PENDING row — never an untracked operation writing real customers into a real store. The HTTP request returns in seconds; the operation is finalized later by reconcile-on-poll. The product flow is the exact twin of this.

409 Store busy

The store lock is taken in the same transaction as the PENDING write. If a colleague is already working that shop the transaction rolls back — no row, no orphan — and the caller gets a 409 to retry, not an error.

boot Resume backstop

A PENDING row means the process died between writing the row and getting a bulk-op id. On the next boot, resumePendingImports either adopts the shop's live operation or relaunches it — deterministically, from the same rows.

TTL Lock lifetime

Each poll that finds the op still running renewStoreLocks. If the last browser walks away, a server-side sweep advances the orphaned run and the lock's TTL frees the store — no shop stays busy forever.
