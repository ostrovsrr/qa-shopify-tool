Full-stack architecture · internal QA tooling

Shopify CSV QA Tool

A single Express server and React client, over one PostgreSQL database, that validates and test-imports Shopify CSV migrations. Two structurally identical flows — Customers and Products — share one Shopify bulk-operation engine. Every import is durable and resumable: the row is written to the database before the side effect ever touches a real store.

Async import lifecycle

Both flows share one state machine. The run is persisted before the bulk op is submitted, so a crash leaves a recoverable PENDING row rather than an untracked mutation writing real records with no trace. Terminal states are reached by reconcile-on-poll; a server-side sweep advances runs whose browser walked away.

PENDING

Row written, bulk op not yet submitted. The durability boundary.

→
RUNNING

Op queued at Shopify; each poll reconciles progress & renews the store lock.

→
COMPLETED

JSONL parsed; per-row / per-product results persisted.

/
FAILED · CANCELED · EXPIRED

Terminal error captured; store lock released, run stays legible.

Load-bearing decisions

The design choices that make a shared, hosted QA tool safe to point at real Shopify stores.

lock One lock per store

Shopify permits a single bulk mutation per shop, and cleanups delete across a whole store by tag. Keying the lock on bare storeId serializes imports vs cleanups on the same shop while N-store batches stay parallel across different shops.

boot Resume & sweep on start

On boot, resumePendingImports adopts or relaunches interrupted runs; orphan uploads are swept, expired PII purged, and stuck cleanups reconciled server-side. A claimedAt claim stops overlapping (rolling-deploy) boots from double-working a row.

pii Uploads are merchant PII

Raw CSVs stream to a temp file and are unlinked by whoever consumes them; previewStore holds only the path. A retention job purges source rows past the window — never while an import still needs them to rebuild its dataset.

audit Attribution ≠ authorization

createdBy and ActionLog exist for display and audit in a deliberately shared workspace — they never gate access. Every destructive action (6 routes) is logged append-only so “who deleted this?” has an answer.
